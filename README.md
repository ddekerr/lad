# Лад

Веб-застосунок для музикантів: база пісень з текстом і акордами, плейлисти, персональні копії, режим сцени. Адаптивний (телефон, планшет, комп'ютер), інтерфейс англійською за замовчуванням з перемикачем на українську.

Вимоги, схема БД і структура бекенду лежать у Project «Лад» (`lad-functional-spec.md`, `lad-db-schema.md`, `lad-backend-spec.md`, `lad-brand-spec.md`).

## Стек

Next.js (App Router, TypeScript), Tailwind CSS 4, PostgreSQL + Prisma, nodemailer для листів.

## Запуск

```bash
npm install
cp .env.example .env          # заповни AUTH_SECRET і SUPER_ADMIN_EMAIL
npx prisma migrate dev --name init
npm run db:seed               # ролі й три демо-пісні
npm run dev                   # http://localhost:3000
```

Перший вхід у розробці: без SMTP код для входу друкується в консоль, де запущено `npm run dev`. Вкажи свою пошту в `SUPER_ADMIN_EMAIL`, увійди нею, і ти отримаєш права адміна й супер-адміна.

Тести: `npm test`. Типи: `npm run typecheck`. Межі архітектури: `npm run lint`.

## Архітектура

Увесь код лежить у `src/` і організований за [Feature-Sliced Design](https://feature-sliced.design). Шари йдуть зверху вниз, кожен імпортує лише з шарів нижче.

| Шар        | Що там                                                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `app`      | Роути Next (App Router): тонкі `page.tsx` з реекспортом зі `views`, `layout.tsx`, `api/**/route.ts`, `globals.css` з токенами брендбука                                              |
| `views`    | Екрани (назва `views` замість `pages`, щоб не конфліктувати з Next): `catalog`, `song`, `song-editor`, `copy`, `playlists`, `playlist`, `profile`, `sign-in`, `users-roles`, `stage` |
| `widgets`  | Великі самодостатні блоки: `song-viewer`, `copy-editor`, `playlist-view`, `song-editor`, `stage-mode`, `users-admin`, `music-roles-admin`, `app-navigation`                          |
| `features` | Дії користувача: `sign-in`, `change-language`, `add-song-to-playlist`, `create-playlist`, `import-songs`                                                                             |
| `entities` | Предметні сутності й чиста логіка: `song`, `song-copy`, `playlist`, `role`, `user` (матриця прав)                                                                                    |
| `shared`   | `ui` (іконки, логотип), `lib/chords` (розбір і транспонування акордів), `i18n` (словники EN/UK)                                                                                      |
| `server`   | Поза FSD: БД (Prisma), сесії й автентифікація, пошта, запити до БД                                                                                                                   |

Правила, які перевіряє `eslint-plugin-boundaries` (`eslint.config.mjs`):

- слайси одного шару не імпортують один одного;
- слайс доступний ззовні лише через свій `index.ts`;
- `server` можуть імпортувати `app`, `views` і `features` (серверні дії); `widgets`, `entities` і `shared` ні;
- `server` залежить лише від `entities` і `shared`;
- у `src/app/**/page.tsx` лишається тільки реекспорт зі `views` і `export const dynamic`: Next не дозволяє реекспортувати налаштування сегмента.

Юніт-тести лежать поруч із кодом (`*.test.ts`). Наскрізні тести (Playwright) ведуться окремо від застосунку.

## Імпорт пісень (JSON)

Кнопка «Імпорт пісень» є на головній сторінці (каталог) і лише в користувачів з роллю Editor. Сервер перевіряє роль сам: `POST /api/songs/import` повертає 401 гостю й 403 без ролі Editor. Приклад файлу: [`docs/song-import.example.json`](docs/song-import.example.json).

Структура файлу:

```json
{
  "songs": [
    {
      "title": "Назва",
      "artist": "Виконавець",
      "language": "uk",
      "originalKey": "Am",
      "body": "[Am]Слова [G]тут\n[F]Другий [E]рядок"
    }
  ]
}
```

| Поле          | Обов'язкове | Правила                                                                   |
| ------------- | ----------- | ------------------------------------------------------------------------- |
| `title`       | так         | рядок, до 200 символів, пробіли по краях обрізаються                      |
| `artist`      | так         | рядок, до 200 символів                                                    |
| `language`    | так         | `"en"` або `"uk"`                                                         |
| `originalKey` | так         | тональність: `C`, `F#`, `Am`, `Bbm` тощо                                  |
| `body`        | так         | текст з акордами в `[дужках]` (ChordPro), до 50 000 символів, не порожній |

Правила розбору:

- **Зайві поля відкидаються**, зокрема службові (`id`, `version`, `createdAt`, `deletedAt`, автор): їх задає сервер. Інші ключі верхнього рівня теж ігноруються. Імена проігнорованих полів показуються у повідомленні про успіх.
- **Відсутнє необов'язкове поле**: пісня зберігається, підставляється значення за замовчуванням, якщо воно є. **Відсутнє обов'язкове**: помилка `missing`. Відсутнім вважається поле, якого немає у файлі, або зі значенням `null`. Порожній рядок і хибне значення (невідома мова, неправильна тональність) це помилка `invalid`.
- **Зараз усі п'ять полів обов'язкові**, бо в схемі немає необов'язкових полів вмісту. Щоб зробити поле необов'язковим, у `SONG_FIELDS` (`src/entities/song/model/song-input.ts`) вкажи `required: false` і за потреби `defaultValue`. Це зачепить і редактор пісень, бо вони діляться одним описом полів.
- **Усе або нічого**: якщо хоч одна пісня не пройшла перевірку, не зберігається жодна, а користувач бачить усі проблеми (номер пісні у файлі, назва, поле, причина). Так виправлений файл можна завантажити ще раз без дублів.
- **Перевірки на дублікати немає**: повторне завантаження того самого коректного файлу створить пісні вдруге.
- Ліміти: до 500 пісень і до 5 МБ в одному файлі. Файл із BOM (Блокнот Windows) приймається.

Відповіді `POST /api/songs/import?format=json` (тіло запиту: вміст файлу):

| Код | Тіло                                                                                                                                      | Коли                                     |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 201 | `{ "imported": 2, "ignoredFields": ["id"] }`                                                                                              | усі пісні збережено                      |
| 422 | `{ "error": "invalid_songs", "items": [{ "index": 2, "title": "…", "issues": [{ "field": "artist", "code": "missing" }] }], "total": 1 }` | є пісні з помилками, нічого не збережено |
| 400 | `{ "error": "invalid_json" \| "invalid_format" \| "no_songs" \| "too_many_songs" \| "unsupported_format" }`                               | файл загалом хибний                      |
| 413 | `{ "error": "too_large" }`                                                                                                                | файл завеликий                           |

Інші формати додаються без змін у перевірці: потрібен розбирач, який повертає список «сирих» пісень (як `parseSongsJson` у `src/entities/song/model/song-import.ts`), і гілка за параметром `format` у `src/app/api/songs/import/route.ts`. Далі пісні проходять ті самі `validateImportedSongs`.

## Статус

Етап 1: каркас, бренд-тема, EN/UK, схема БД, каталог, перегляд пісні, транспонування акордів, режим сцени, публічне API пісень.

Етап 2: вхід через email-код і Google, сесії на 1 місяць, профіль, матриця прав, адмінка ролей (Admin), довідник музичних ролей (супер-адмін), підрахунок наслідків перед зняттям музичної ролі.

Етап 3: плейлисти в контексті музичної ролі або «без ролі», персональні копії пісень (нотатки, зсув тональності, власні правки), одна кнопка «Оновити згідно з оригіналом», «Залишити як власну», режим сцени з переходом між піснями плейлиста, порядок пісень стрілками.

Етап 4: редактор пісень для ролі Editor: додавання, редагування з живим переглядом акордів, м'яке видалення; `version` зростає лише при зміні вмісту, тож копії користувачів отримують стан «оригінал оновили». API: `POST /api/songs`, `PATCH`/`DELETE /api/songs/{id}`.

Етап 5 (поточний): імпорт пісень із JSON для ролі Editor (кнопка в каталозі, `POST /api/songs/import`), див. розділ «Імпорт пісень (JSON)».

Далі: перевірка в живому середовищі (npm install, міграції, e2e-тести), швидкість входу, імпорт в інших форматах.

## Рішення, що відрізняються від backend-spec v0.2

- Сесія це один непрозорий токен у httpOnly cookie з терміном 1 місяць; у БД лише його хеш (таблиця `refresh_tokens`). Окремого короткого access-токена немає: перевірка йде по БД на кожен запит, відкликання (вихід) миттєве.
- Ролями в API керують за `roleId` (як у специфікації); довідник музичних ролей має ще `GET /api/roles/{id}/impact`.

## Примітки

- Транспонування акордів (`src/shared/lib/chords`), права (`src/entities/user/model/permissions.ts`), хеші кодів і словники покриті тестами.
- Код написано без запуску Next.js і Prisma (у середовищі розробки був закритий npm), тому перший `npm install`, `migrate` і `dev` можуть виявити дрібні помилки.
