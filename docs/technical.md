# Лад: технічна документація

Для розробників. Описує інструменти, технології, архітектуру, запуск і збирання, а також повний список можливостей застосунку з технічного боку.

Інші документи: [дизайн](design.md), [посібник для музикантів](musicians-guide.md).

## 1. Що це

Веб-застосунок для музикантів: база пісень із текстом і акордами, плейлисти під музичні ролі, персональні копії пісень, транспонування, режим сцени. Адаптивний (телефон, планшет, комп'ютер). Інтерфейс англійською за замовчуванням і українською.

## 2. Технології та інструменти

| Область        | Що використовується                                                                                         |

| Мова           | TypeScript (strict)                                                                                         |

| Пошта          | nodemailer 7 (SMTP)                                                                                         |

| Тести          | вбудований `node:test`, запуск через `tsx`                                                                  |

Окремих HTTP-клієнтів чи стейт-менеджерів немає: клієнтські компоненти використовують `fetch` і локальний стан React; дані на сторінках читаються на сервері.

## 3. Архітектура

### 3.1 Feature-Sliced Design

Увесь код лежить у `src/` і організований за [Feature-Sliced Design](https://feature-sliced.design). Шари йдуть зверху вниз, кожен імпортує лише з шарів нижче.

| Шар        | Призначення                                                                                           | Зараз                                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `app`      | Роути Next: тонкі `page.tsx` з реекспортом зі `views`, `layout.tsx`, `api/**/route.ts`, `globals.css` | групи `(main)` (з оболонкою) і `(stage)` (режим сцени), `api/`                                                                   |
| `views`    | Екрани. Назва `views` замість `pages`, щоб не конфліктувати з Next                                    | `catalog`, `song`, `song-editor`, `copy`, `playlists`, `playlist`, `profile`, `sign-in`, `users-roles`, `stage`                  |
| `widgets`  | Великі самодостатні блоки інтерфейсу                                                                  | `song-viewer`, `song-editor`, `copy-editor`, `playlist-view`, `stage-mode`, `users-admin`, `music-roles-admin`, `app-navigation` |
| `features` | Дії користувача                                                                                       | `sign-in`, `change-language`, `add-song-to-playlist`, `create-playlist`, `import-songs`                                          |
| `entities` | Предметні сутності й чиста логіка                                                                     | `song`, `song-copy`, `playlist`, `role`, `user` (матриця прав)                                                                   |
| `shared`   | Багаторазове без прив'язки до предмета                                                                | `ui` (іконки, логотип), `lib/chords` (розбір і транспонування), `i18n` (словники)                                                |
| `server`   | Поза FSD: доступ до БД, автентифікація, пошта, запити                                                 | `db.ts`, `auth/*`, `mail.ts`, `songs.ts`, `playlists.ts`, `roles.ts`, `i18n.ts`                                                  |

Структура слайса: `ui/` (компоненти), `model/` (чиста логіка й типи), `api/` (серверні дії), назовні лише через `index.ts`.

### 3.2 Правила залежностей

Перевіряє `eslint-plugin-boundaries` (`eslint.config.mjs`), порушення дають помилку лінтера:

- слайси одного шару не імпортують один одного;
- слайс доступний ззовні лише через свій `index.ts` (публічний API);
- `server` можуть імпортувати `app`, `views` і `features` (серверні дії), а `widgets`, `entities` і `shared` ні;
- `server` залежить лише від `entities` і `shared`;
- у `src/app/**/page.tsx` лишається тільки реекспорт зі `views`; `export const dynamic = 'force-dynamic'` лишається в роут-файлі, бо Next не дозволяє реекспортувати налаштування сегмента.

Додатково `eslint-plugin-check-file` вимагає імен файлів у kebab-case (екрани мають суфікс `.page.tsx`), а typescript-eslint вимагає імен типів у PascalCase.

### 3.3 Патерни

- **Чиста логіка окремо від БД.** Правила (права, версії копій, імпорт, перевірка введення, транспонування) це чисті функції в `entities/*/model` і `shared/lib`, вони покриті юніт-тестами. Роути лише викликають їх і працюють із Prisma.
- **Серверні компоненти за замовчуванням.** Сторінки читають дані на сервері; клієнтські компоненти (`'use client'`) лише там, де є стан і події: перегляд пісні, режим сцени, редактори, форми.
- **Опис полів як дані.** `FieldSpec` / `parseFields` у `src/entities/song/model/song-input.ts` задає, які поля пісні обов'язкові й як їх чистити; ту саму перевірку використовують редактор і імпорт.
- **Мова з cookie.** Сервер визначає мову (`getLocale`), словники EN/UK мають однакові ключі (перевіряє тест); тексти з підстановками проходять через `fmt`.
- **Права як матриця.** `can(actor, action)` у `entities/user/model/permissions.ts` єдине місце, де вирішується, хто що може; роути викликають його замість прямих перевірок ролей.
- **Єдині відповіді помилок API:** `{ "error": "<код>" }`, для 403 ще `reason`; коди 400, 401, 403, 404, 409, 413, 422.

## 5. Запуск і збирання

### 5.1 Підготовка

Потрібні Node.js 20+ і PostgreSQL (локально чи хмарний).

```bash
git clone https://github.com/ddekerr/lad.git
cd lad
npm install
cp .env.example .env     # заповни значення, див. розділ 5.2
npx prisma migrate dev   # створює таблиці
npm run db:seed          # ролі (Member, Editor, Admin, басист, співак, піаніст) і три демо-пісні
npm run dev              # http://localhost:3000
```

Перший вхід у розробці: якщо `SMTP_HOST` порожній, код входу друкується в консоль, де запущено `npm run dev` (рядок `[mail:dev] Login code for …`). Вкажи свою пошту в `SUPER_ADMIN_EMAIL`, увійди нею, і ти отримаєш права адміна й супер-адміна. Роль Editor видає адмін на сторінці «Користувачі».

## 6. Автентифікація і права

- **Способи входу:** Google OAuth (`/api/auth/google` → `/callback`) і одноразовий код на email. Обидва ведуть в один акаунт за адресою пошти.
- **Код із листа:** 6 цифр, діє 10 хвилин, 5 спроб на код, не більше 5 запитів коду на email за 15 хвилин; у БД лише хеш коду (з `AUTH_SECRET`), використання атомарне.
- **Сесія:** один непрозорий токен у httpOnly cookie `lad_session` (SameSite=Lax) на 30 днів; у таблиці `refresh_tokens` лише його хеш. Перевірка йде по БД на кожен запит, тож вихід відкликає сесію одразу.
- **Супер-адмін** визначається за email у `.env`, у БД не зберігається, завжди має роль Admin, яку не можна зняти.
- **Ролі не кумулятивні:** гість, Member (є в усіх зареєстрованих і не знімається), музичні ролі (басист, співак, піаніст та додані супер-адміном), Editor, Admin.

Матриця прав (`can`):

| Дія                                                                                 | Хто                  |
| ----------------------------------------------------------------------------------- | -------------------- |
| переглядати пісні (`song:read`)                                                     | усі, навіть гість    |
| додавати, змінювати, видаляти, імпортувати пісні (`song:write`)                     | Editor               |
| керувати власними плейлистами й копіями (`playlist:manage`)                         | будь-який користувач |
| бачити список користувачів (`users:read`), видавати й знімати ролі (`roles:assign`) | Admin і супер-адмін  |
| керувати довідником музичних ролей (`musicRoles:manage`)                            | лише супер-адмін     |

Додаткові правила видачі ролей: Member автоматичний і не знімається; роль Admin видає й знімає лише супер-адмін; роль супер-адміна зняти не можна. Перед зняттям музичної ролі показується кількість плейлистів і копій, які буде видалено.

## 7. Модель даних

Схема: `prisma/schema.prisma`; таблиці й ключові поля:

| Таблиця           | Призначення                                                                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`           | email (унікальний, нижній регістр), мова інтерфейсу `en`/`uk`, `last_login_at`                                                               |
| `auth_identities` | способи входу користувача (`google`/`email`)                                                                                                 |
| `login_codes`     | хеші одноразових кодів, `expires_at`, `attempts`, `used_at`                                                                                  |
| `refresh_tokens`  | хеші токенів сесій, `expires_at`, `revoked_at`, `user_agent`                                                                                 |
| `roles`           | довідник ролей: ключ, вид `system`/`music`, назви EN/UK, `is_removable`                                                                      |
| `user_roles`      | ролі користувачів, хто видав і коли                                                                                                          |
| `songs`           | назва, виконавець, мова, оригінальна тональність, текст з акордами (`body`), `version`, `deleted_at`                                         |
| `playlists`       | власник, музична роль (або порожньо = «без ролі»), назва                                                                                     |
| `song_copies`     | копія пісні в плейлисті: свої `title/artist/language/original_key/body`, `key_shift`, `notes`, `synced_version`, `is_standalone`, `position` |

Каскади: видалення користувача прибирає його ролі, входи, токени, плейлисти й копії; видалення плейлиста (чи музичної ролі) прибирає копії; видалення пісні м'яке (`deleted_at`), копії лишаються.

### Формат тексту пісні

Стиль ChordPro: акорд у квадратних дужках перед складом, де він змінюється, `[Am]Слова [G]тут`. Рядки розділяються `\n`, порожній рядок це відступ. До 50 000 символів. Розбір: `src/shared/lib/chords/parse.ts` (рядок → фрагменти «акорд + текст»).

### Версіонування й копії

- `songs.version` зростає лише коли змінився вміст (назва, виконавець, мова, тональність, текст).
- Копія зберігає `synced_version`; стан виводиться, окремого поля немає:
  - `standalone`: `is_standalone = true`;
  - `original_deleted`: оригінал видалено (чи зв'язок зник);
  - `outdated`: `songs.version > synced_version`;
  - `current`: версії збігаються.
- «Оновити згідно з оригіналом» замінює назву, виконавця, мову, оригінальну тональність і текст; нотатки й зсув тональності не чіпає. «Залишити як власну» обнуляє зв'язок з оригіналом.
- Копія зберігається в тональності оригіналу, зсув окремо, тому оновлення не губить обрану тональність.

## 8. Транспонування

`src/shared/lib/chords/transpose.ts`: англійська літерна нотація (C D E F G A B), дієзи й бемолі, акорд розбирається на основну ноту, якість (m, 7, sus тощо) і бас після скісної риски (`C/E`). Невпізнаний акорд повертається без змін. Вибір дієзів чи бемолів залежить від цільової тональності (наприклад, F, Bb, Eb, Ab, Db та Dm, Gm, Cm, Fm, Bbm, Ebm пишуться з бемолями). Транспонування відбувається на клієнті й не змінює пісню в базі.

## 9. Імпорт пісень (JSON)

Кнопка «Імпорт пісень» у каталозі, лише для Editor; сервер перевіряє роль сам. Приклад файлу: [`song-import.example.json`](song-import.example.json).

```json
{
  "songs": [
    {
      "title": "Назва",
      "artist": "Виконавець",
      "language": "uk",
      "originalKey": "Am",
      "body": "[Am]Слова [G]тут\n[F]Другий [E]рядок"
    }
  ]
}
```

| Поле          | Обов'язкове | Правила                                                        |
| ------------- | ----------- | -------------------------------------------------------------- |
| `title`       | так         | рядок, до 200 символів, пробіли по краях обрізаються           |
| `artist`      | так         | рядок, до 200 символів                                         |
| `language`    | так         | `"en"` або `"uk"`                                              |
| `originalKey` | так         | тональність: `C`, `F#`, `Am`, `Bbm` тощо                       |
| `body`        | так         | текст з акордами в `[дужках]`, до 50 000 символів, не порожній |

- **Зайві поля відкидаються** (також службові: `id`, `version`, автор тощо), їхні імена показуються в повідомленні про успіх.
- Відсутнє необов'язкове поле дає значення за замовчуванням (якщо воно задане), відсутнє обов'язкове дає помилку `missing`. Відсутнє це немає поля або `null`; порожній рядок і хибне значення дають `invalid`. Зараз усі п'ять полів обов'язкові; щоб зробити поле необов'язковим, у `SONG_FIELDS` вкажи `required: false` і за потреби `defaultValue` (це зачепить і редактор).
- **Усе або нічого:** якщо хоч одна пісня не пройшла перевірку, не зберігається жодна; користувач бачить усі проблеми (номер пісні, назва, поле, причина), тож виправлений файл можна завантажити ще раз без дублів.
- Перевірки на дублікати немає: повторний коректний файл створить пісні вдруге.
- Ліміти: до 500 пісень, до 5 МБ; файл із BOM приймається.

`POST /api/songs/import?format=json` (тіло: вміст файлу):

| Код      | Тіло                                                                                 | Коли                                     |
| -------- | ------------------------------------------------------------------------------------ | ---------------------------------------- |
| 201      | `{ "imported": 2, "ignoredFields": ["id"] }`                                         | усі пісні збережено                      |
| 422      | `{ "error": "invalid_songs", "items": [...], "total": 1 }`                           | є пісні з помилками, нічого не збережено |
| 400      | `invalid_json`, `invalid_format`, `no_songs`, `too_many_songs`, `unsupported_format` | файл загалом хибний                      |
| 413      | `{ "error": "too_large" }`                                                           | файл завеликий                           |
| 401, 403 | `unauthorized`, `forbidden`                                                          | гість; користувач без ролі Editor        |

Додати інший формат: розбирач, що повертає список «сирих» пісень (як `parseSongsJson` у `src/entities/song/model/song-import.ts`), і гілка за параметром `format` у `src/app/api/songs/import/route.ts`; далі працює та сама `validateImportedSongs`.

## 10. API

Усі відповіді JSON. Права вказані мінімальні; помилки: 401 (немає входу), 403 (немає прав), 404, 400/422 (хибне введення).

| Метод і шлях                                | Хто                 | Що робить                                                                 |
| ------------------------------------------- | ------------------- | ------------------------------------------------------------------------- |
| `GET /api/songs?q=`                         | усі                 | каталог із пошуком за назвою й виконавцем                                 |
| `POST /api/songs`                           | Editor              | створити пісню                                                            |
| `GET/PATCH/DELETE /api/songs/{id}`          | усі / Editor        | прочитати; змінити (версія зростає лише при зміні вмісту); м'яко видалити |
| `POST /api/songs/import?format=json`        | Editor              | імпорт (розділ 9)                                                         |
| `POST /api/auth/email/request`, `/verify`   | усі                 | запитати код на пошту, перевірити код і створити сесію                    |
| `GET /api/auth/google`, `/google/callback`  | усі                 | вхід через Google                                                         |
| `POST /api/auth/logout`                     | користувач          | вийти, відкликати сесію                                                   |
| `GET/PATCH /api/me`                         | користувач          | профіль і мова інтерфейсу                                                 |
| `GET/POST /api/playlists`                   | користувач          | свої плейлисти (фільтр `?role=`), створити                                |
| `GET/PATCH/DELETE /api/playlists/{id}`      | власник             | прочитати, перейменувати, видалити з копіями                              |
| `POST /api/playlists/{id}/songs`            | власник             | додати пісню: створюється нова копія                                      |
| `PATCH /api/playlists/{id}/songs/order`     | власник             | змінити порядок копій (має містити ті самі id)                            |
| `GET/PATCH/DELETE /api/copies/{id}`         | власник             | копія: назва, виконавець, текст, нотатки, зсув тональності                |
| `POST /api/copies/{id}/refresh`             | власник             | оновити згідно з оригіналом                                               |
| `POST /api/copies/{id}/keep`                | власник             | залишити як власну                                                        |
| `GET /api/users?search=`                    | Admin               | список користувачів                                                       |
| `POST /api/users/{id}/roles`                | Admin               | видати роль (роль Admin лише супер-адмін)                                 |
| `DELETE /api/users/{id}/roles/{roleId}`     | Admin               | зняти роль                                                                |
| `GET /api/users/{id}/roles/{roleId}/impact` | Admin               | скільки плейлистів і копій зникне при знятті ролі                         |
| `GET/POST /api/roles`                       | Admin / супер-адмін | довідник ролей; додати музичну роль                                       |
| `PATCH/DELETE /api/roles/{id}`              | супер-адмін         | перейменувати, прибрати музичну роль                                      |
| `GET /api/roles/{id}/impact`                | супер-адмін         | наслідки видалення ролі                                                   |

Ліміти введення: назва й виконавець до 200 символів, текст до 50 000, нотатки до 5 000, назва плейлиста до 80; ключ ролі не може бути зарезервованим (`member`, `editor`, `admin`, `super-admin`, `guest`).

## 11. Список функцій застосунку

**Гість**

- Перегляд каталогу й пошук за назвою та виконавцем.
- Перегляд пісні: режими «Текст», «Акорди», «Текст і акорди»; транспонування з кнопками − і + та скиданням; режим сцени.
- Вхід через Google чи email-код; перемикач мови.

**Користувач (Member)**

- Профіль: пошта, мова, ролі.
- Плейлисти в контексті музичної ролі користувача або «без ролі»: створення, перейменування, видалення з підтвердженням; порядок пісень стрілками.
- Додавання пісні з каталогу в плейлист (створюється персональна копія).
- Копія: нотатки, власний зсув тональності, правка назви, виконавця й тексту; стани «оригінал оновлено» і «оригінал видалено» з діями «Оновити згідно з оригіналом», «Залишити як власну», «Видалити копію»; видалення копії.
- Режим сцени для пісні й для плейлиста: великий текст (20–80 px), зміна тональності, автопрокрутка зі швидкістю 1–10, паузa дотиком, автоматичне приховування панелей, «Попередня»/«Наступна» пісня плейлиста, екран не гасне (Wake Lock).

**Editor**

- Додавання, редагування й м'яке видалення пісень; живий перегляд акордів у редакторі; перевірка тональності й полів.
- Імпорт пісень із JSON.

**Admin**

- Список користувачів із пошуком; видача й зняття ролей (Editor, музичні), підрахунок наслідків перед зняттям музичної ролі.

**Супер-адмін**

- Довідник музичних ролей: додати, перейменувати (EN і UK), прибрати з підрахунком наслідків.
- Видача й зняття ролі Admin.

**Наскрізне**

- Двомовний інтерфейс EN/UK, мова зберігається у профілі та cookie.
- Адаптивна розкладка: бічна панель на комп'ютері, нижня панель на телефоні.
- Доступність: фокус, `aria`, поважається «зменшити рух» (див. [дизайн](design.md)).

## 12. Тести та якість

- Юніт-тести лежать поруч із кодом (`*.test.ts`): права й видача ролей, логіка копій і порядку, перевірка введення пісень, копій, плейлистів і ролей, імпорт пісень, хешування кодів, акорди й транспонування, словники EN/UK (однакові ключі й підстановки).
- Наскрізні тести (Playwright) ведуться окремо від застосунку й ще не створені.
- Перед пул-реквестом: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.

## 13. Відомі обмеження й плани

- Код розроблявся без доступу до npm у середовищі автора, тому перший повний прогін (`npm install`, `lint`, `typecheck`, `build`, міграції) може виявити дрібні помилки.
- Імпорт лише JSON; інші формати додаються за схемою розділу 9. Дублікатів при імпорті не відсікаємо.
- Немає світлої теми, PWA-іконки, e2e-тестів, історії змін пісень, журналу дій адміна.
- **Заплановано, але не реалізовано:** генерація партії для інструмента (наприклад, басу) за акордами й параметрами. Партії існуватимуть лише в копії музиканта, максимум по одній на рівень складності (Easy, Medium, Hard). Потрібні параметри: тональність, розмір, BPM, динаміка 1–5 для кожного розділу пісні; без них генерація повертає помилку з переліком відсутнього. Опис для музикантів у [посібнику](musicians-guide.md), розділ «Заплановано».
